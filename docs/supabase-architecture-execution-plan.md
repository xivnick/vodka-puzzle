# Supabase 부하 개선 요구사항

작성일: 2026-11-18 KST. 전체 개선 작업의 목표와 완료 조건을 정의한다.

## 목표

자정에 접속·보상 수령·뽑기·꾸미기가 겹쳐도 조회와 계산을 효율적으로 처리해 안정적인 응답을 제공한다. 기존 기능과 데이터의 정확성을 유지하면서 전체 요청 흐름을 개선한다.

대상은 개인 상태 조회, 거래 후 갱신, 업적 계산, 공통 목록·순위, 날짜 전환, 동시 거래다. 전체 대상을 함께 개선한다. 완료 여부는 각 대상의 동작과 측정 결과가 아래 요구사항을 충족하는지로 판단한다.

## 정확성과 갱신 시점

- 잔액·아이템 소유·보상 자격·거래 결과는 서버가 행동을 처리하는 시점의 상태를 기준으로 정확하게 판정한다.
- 완료된 행동의 개인 상태는 성공 응답 후 화면에 반영한다. 처리 중이거나 결과 확인이 필요한 경우에는 그 상태를 표시한다.
- 헤더 알림·업적 표시·공통 목록·순위는 정한 갱신 주기 안에 반영한다. 본인 행동으로 확인된 변경은 해당 응답을 받으면 반영한다.
- 표시 정보의 허용 지연은 현재 갱신 주기를 확인해 명시한다. 기존 주기 이내를 기본으로 하며, 변경이 필요하면 사용자 영향과 함께 정한다. 공개 시각과 거래 판정은 서버의 실제 시각과 조건을 따른다.

## 필요한 동작

### 1. 같은 정보는 함께 사용한다

- 같은 화면에서 헤더와 본문이 필요로 하는 동일한 정보는 진행 중 요청과 조회 결과를 공유한다.
- 로그인 준비·탭 복귀·날짜 전환처럼 겹치는 자동 갱신은 동일한 조회로 합친다.
- 현재 화면에 필요한 범위의 계정 정보를 가져온다.

### 2. 행동의 결과가 화면에 일관되게 반영된다

- 보상 수령·뽑기·조합·장착의 결과와 관련 잔액·아이템·장비·업적·알림은 위 갱신 기준에 따라 일관되게 표시한다.
- 받은 행동 결과를 화면에 적용하고, 갱신에 필요한 추가 정보만 가져온다.
- 응답 도착 순서와 관계없이 확인된 상태 중 가장 최신 상태를 유지한다. 다른 탭의 변경도 화면 복귀 또는 다음 행동 전에 반영하거나 충돌을 감지한다.
- 계정 전환 시 표시 정보와 응답 적용 대상을 현재 계정으로 한정한다.

### 3. 업적 계산 결과를 재사용한다

- 업적 화면과 헤더는 원본 기록·규칙·적용 날짜·공개 조건이 동일한 동안 기존 진행 상태 계산 결과를 재사용한다.
- 행동이 영향을 주는 업적만 갱신한다. 복잡한 업적은 관련 상태를 재계산하는 방식도 허용한다.
- 완료 기록 수정·제외·삭제, 퍼즐 공개, 규칙 변경, 시즌·날짜 전환 이후에도 진행 상태와 보상 자격이 정확해야 한다. 예약 공개처럼 시간이 지나 발생하는 변화도 포함한다.
- 재사용하는 진행 상태는 원본 기록에서 복구할 수 있어야 한다. 복구와 초기화는 기존 보상 지급 내역을 보존하고 진행 상태를 재구성한다.

### 4. 공통 조회의 계산 비용을 공유한다

- 최근 완료와 순위 등 계산 비용이 큰 공통 집계는 결과를 여러 사용자가 공유한다.
- 공통 결과에는 공개 정보만 포함하고 개인 정보는 해당 계정의 권한으로 제공한다. 미공개 퍼즐이나 정답이 노출되지 않는다.
- 결과가 없거나 갱신에 실패한 경우를 포함해, 동시 조회가 늘어도 같은 공통 집계의 계산 횟수는 제한된다.

### 5. 자정과 동시 요청을 안전하게 처리한다

- 자동 갱신과 재시도 시점을 분산한다. 화면이 표시된 동안 필요한 정보를 갱신하고, 숨겨진 화면은 복귀 시 최신 상태를 확인한다.
- 사용자가 직접 실행하는 행동은 자동 갱신의 지연 정책과 분리해 처리하고 처리 상태를 표시한다.
- 서로 다른 사용자의 독립 거래는 병렬로 처리할 수 있어야 한다. 공유 순위·발행 등 실제로 보호해야 하는 동시성 조건은 유지한다.
- 통신 실패·중복 요청·여러 탭의 동시 행동에도 거래당 지급과 차감은 한 번만 반영하고, 잔액은 0 이상으로 유지하며, 아이템 보유 내역은 완료된 거래와 일치해야 한다.

## 유지해야 할 조건

- 보상 조건·가격·확률·환급·공개 일정·순위·스트릭의 기존 의미를 보존한다.
- Supabase와 기존 배포 환경 안에서 해결하는 것을 기본으로 한다. 구현 수단은 현재 데이터 규모와 측정 결과에 맞춰 가장 단순한 것을 선택한다.
- 서비스 운영 중 전환할 수 있어야 하며, 이미 열려 있는 탭도 안전하게 동작해야 한다. 초기 데이터 준비 전후의 모든 거래가 전환된 상태에 반영되어야 한다.
- 배포 문제가 생기면 완료된 거래와 사용자 기록을 보존하면서 이전 동작으로 복구할 수 있어야 한다.
- 기존 권한과 개인정보 보호를 유지한다. 계정 삭제 시 새로 보관한 개인 정보도 정리한다.

## 완료 판단

다음 근거를 간단한 결과 보고로 남긴다. 기존 검증 도구와 진단을 우선 활용한다.

1. 위 다섯 대상별로 충족한 요구사항과 실제 변경 내용을 설명한다. 기존 방식으로 충족한 부분도 근거를 남긴다.
2. 초기 진입, 보상 수령, 뽑기·장착, 탭 복귀, 자정 전환의 요청 수와 반복 계산이 어떻게 줄었는지 비교한다. 동일 조건의 반복 측정으로 요청·계산 감소와 응답 성능을 비교하고 기능 회귀를 확인한다. 성능 저하가 관측되면 원인을 확인해 조치하고, 결과를 판단하기에 표본이 부족하면 추가 관측 대상으로 명시한다.
3. 중복 거래, 동시 거래, 계정 전환, 날짜 경계, 기록·규칙 변경, 구형 탭에서 정확성과 권한을 검증한다. 파생 데이터를 도입했다면 기존 계산과 대조한다.
4. 운영 배포와 복구 준비를 완료하고 자정 전후 결과를 확인한다. 관측이 남아 있으면 구현 완료와 운영 검증 대기를 구분한다. 확인된 개선 효과와 남은 장애 원인을 각각 명시한다.
