# 빼빼로 쿠지

예시: https://puzzle.xivnick.me/test/pepero-kuji/

예시는 브라우저 저장소로 동작한다. 실제 계정과 완료 기록은 연결하지 않는다. 운영 DB에는 `supabase/migrations/20261111_pepero_kuji.sql`과 `20261111_pepero_kuji_cutoff.sql`을 적용했다. 이벤트는 `test` 상태이며 실제 추첨은 활성화하지 않았다.

## DB 구조

| 테이블 | 역할 |
| --- | --- |
| `private.kuji_events` | 이벤트, 대상 시즌·퍼즐, 완료 마감 시각, 상태(test/active/closed) |
| `private.kuji_ticket_grants` | 계정별 1회 참여권, 자격을 얻은 완료 시각, 지급 시각 |
| `private.kuji_prizes` | 상품명·등급·표시 순서 |
| `private.kuji_tickets` | 쿠폰 번호·숨긴 상품·받은 계정·받은 시점의 닉네임·추첨 시각 |

A상 2종 각 1개, B상 5종 각 2개로 총 12장을 생성하고 상품을 무작위 배정한다. 참여권은 한국 시간 2026-11-11 오전 11:11:00까지(해당 시각 포함) 빼빼로 스도쿠를 완료한 Google 계정 9개에 각 1장 지급했다. 11:11:00 이후 완료 기록은 대상이 아니다. 계정별 유일 제약으로 중복 지급을 막으며, 이후 완료에 따른 자동 지급은 없다. 수량은 티켓 행 수로 관리하며 총수량과 남은 수량을 따로 저장하지 않는다.

`kuji_context(event)`는 상품별 수량·티켓 상태·본인 남은 참여권(`remaining_tickets`: 0 또는 1)을 반환한다. 미개봉 티켓의 상품 정보와 계정 UUID는 반환하지 않는다. `open_kuji_ticket(event, number)`는 Google 로그인, 지급된 참여권, 마감 시각까지의 `261111_01` 완료 기록(제외되지 않은 기록)을 확인하고 선택한 쿠폰을 개봉한다.

이벤트 행 잠금으로 동시 추첨을 직렬화하고, `(event_id, claimed_by)` 유일 제약으로 계정당 1회를 보장한다. 재시도는 기존 결과를 반환하며 다른 쿠폰을 다시 열지 않는다. 받은 계정이 삭제되어도 티켓은 개봉 상태로 유지한다. 닉네임은 수령 당시 값으로 보관한다. 상품 테이블과 티켓 테이블은 브라우저에서 직접 읽거나 수정할 수 없다.

운영 화면 연결과 이벤트의 `active` 전환은 별도 공개 승인 후 진행한다. 초기 상태는 `test`이며 공개 RPC로 접근할 수 없다. 클라이언트는 추첨 전에 결과를 결정하지 않고 RPC에서 받은 결과로 연출한다. 네트워크가 끊기면 context를 다시 조회해 본인의 결과를 복구한다.

`python3 scripts/verify-pepero-kuji.py`는 권한·미개봉 상품 비공개·마감 직전/정각/직후의 자격·참여권 지급 여부·사용 후 잔여 수량·중복 요청·품절 쿠폰 충돌·결과 복구를 트랜잭션 안에서 확인한 뒤 모두 롤백한다. 초기 마이그레이션 적용 전에는 `--rehearse`로 두 마이그레이션까지 포함해 검증한다. 검증에 사용한 계정과 추첨은 남기지 않는다.
